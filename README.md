# GDG on Campus TUM — Hackathons & Solutions Challenge

**Semester programme:** 19 October – 14 December 2026  
**Programme pathway:** **IDEA → BUILD → PITCH → IMPACT**

Welcome to the Hackathons & Solutions Challenge repository for Google Developer Groups (GDG) on Campus at the Technical University of Mombasa (TUM). This repository is the shared guide for members preparing for hackathons, the Google Solution Challenge, and other innovation opportunities during the semester.

The programme is designed to make hackathons approachable for beginners while helping members turn real problems into practical, testable technology solutions. It combines a two-week learning roadmap, cross-track buildathon challenges, shared learning resources, and a clear path from idea discovery to demo readiness.

## Programme goals

By the end of the semester, members should be better able to:

- Understand the hackathon process and feel confident joining as beginners.
- Discover real user problems and develop clear problem statements.
- Align ideas with relevant UN Sustainable Development Goals (SDGs) and intended impact.
- Form balanced teams with complementary skills and clear responsibilities.
- Turn ideas into minimum viable products (MVPs) and prototypes.
- Practise with Google developer technologies and tools appropriate to each project.
- Test ideas, gather feedback, and improve solutions.
- Communicate a solution through a concise pitch, demo, and project story.
- Prepare for external hackathons and the Google Solution Challenge.
- Continue promising projects beyond a competition where there is potential.

## Semester roadmap: 19 October – 14 December 2026

The programme is organised into **four two-week blocks**. Each block builds on the previous one. Dates indicate the planning window; exact event dates and delivery formats should be confirmed in the groups.

| Block | Dates | Focus | Expected progress |
|---|---|---|---|
| 1 | 19 October – 1 November | Foundations, problem discovery, SDGs and team formation | Understand hackathons, identify problems, draft problem statements and form teams |
| 2 | 2 – 15 November | Ideation, solution design, MVP planning and technology selection | Select a problem and users, map the solution, define MVP scope and plan a build |
| 3 | 16 – 29 November | Build with Google, prototype development, validation and iteration | Build an early prototype, test key assumptions and record feedback |
| 4 | 30 November – 14 December | Pitching, demo practice, final testing and competition readiness | Refine the prototype, prepare a pitch and demo, and identify next steps |

### Block 1 — Foundations & problem discovery
**19 October – 1 November**

**Focus:** Hackathon Foundations; Ideation & Problem Discovery; SDG & Impact Alignment; Team Formation.

Suggested activities:
- Introduce the hackathon journey, common formats, judging criteria and teamwork expectations.
- Run a problem-discovery exercise based on challenges students or communities experience.
- Turn broad concerns into specific, understandable problem statements.
- Identify relevant SDGs, intended beneficiaries and possible impact measures.
- Help members connect with teammates and agree on roles.

**By the end of the block, aim to have:**
- A one-paragraph problem statement.
- A clearly described target user or beneficiary.
- A first-pass SDG/impact rationale.
- A team roster with initial roles, or an individual idea seeking teammates.

### Block 2 — From idea to MVP
**2 – 15 November**

**Focus:** Solution design; user journeys; MVP thinking; technology selection; project planning.

Suggested activities:
- Compare multiple solution ideas before committing to one.
- Map a simple user journey and the main problem-solving workflow.
- Define the smallest useful version of the product.
- Choose a track and technologies based on the problem, team skills and available time.
- Create a task board, milestones and a simple project README.

**By the end of the block, aim to have:**
- A selected solution concept and value proposition.
- A basic user journey, wireframe, architecture sketch or equivalent plan.
- A prioritised MVP feature list.
- A team task board and build plan.

### Block 3 — Build, validate & iterate
**16 – 29 November**

**Focus:** Practical building; Google developer technologies; testing; feedback; iteration.

Suggested activities:
- Build the core user flow before adding optional features.
- Use relevant Google developer tools where they fit the solution.
- Hold short progress check-ins and surface blockers early.
- Test the prototype with teammates or intended users where feasible.
- Record feedback, bugs, assumptions and changes made.

**By the end of the block, aim to have:**
- A working prototype or demonstrable proof of concept.
- A short record of tests, feedback and known limitations.
- A prioritised list of improvements.
- A clear explanation of what has been built and what remains.

### Block 4 — Pitch, demo & competition readiness
**30 November – 14 December**

**Focus:** Pitch & Communication; Demo & Competition Readiness; sustainability and next steps.

Suggested activities:
- Explain the problem, target users, solution, differentiation and expected impact.
- Prepare a concise pitch deck and a reliable demo flow.
- Rehearse within the time limit and gather peer feedback.
- Test the project from a clean start and prepare a backup demo.
- Review judging criteria and any relevant external competition requirements.
- Discuss project sustainability, future validation and continuation.

**By the end of the block, aim to have:**
- A concise pitch deck or presentation.
- A rehearsed live demo or recorded backup.
- A project repository with setup instructions and known limitations.
- A next-steps plan for validation, iteration or external competition submission.

## Tracks and weekly buildathons

The club will run short, practical buildathon challenges across the following tracks:

1. **Web Development**
2. **Cloud Computing**
3. **Mobile Development**
4. **AI & Machine Learning** — one combined track
5. **Cybersecurity**

There will be **at least two buildathon challenges per week**. Challenge prompts, rules, timelines and submission instructions will be shared in the official GDG groups. This repository includes starter challenge templates in [`challenges/`](challenges/) that organisers can customise and publish.

### How buildathons work

1. Watch the official group for the new challenge announcement.
2. Read the relevant track file and the challenge-specific instructions.
3. Check the deadline, required deliverables and evaluation criteria.
4. Build individually or with a team, as specified in the announcement.
5. Submit the required link, files, demo or write-up using the announced method.
6. Review feedback and use what you learned in the next challenge.

**Important:** The challenge files in this repository are reusable templates and starter prompts. They are not a substitute for the official weekly announcement. Do not assume a challenge is active until it is announced by the organisers.

## The hackathon journey

The programme follows this pathway:

**DISCOVER → IDEATE → TEAM UP → BUILD → VALIDATE → PITCH → COMPETE → IMPACT**

| Stage | What it means |
|---|---|
| Hackathon foundations | Understand the format, process, judging and collaboration expectations |
| Ideation and problem discovery | Find a real problem and describe it clearly |
| SDG and impact alignment | Identify beneficiaries, relevant SDGs and intended outcomes |
| Team formation | Agree on roles, strengths, responsibilities and communication |
| From idea to MVP | Scope a realistic first version and select appropriate technologies |
| Build with Google | Explore relevant Google developer tools through practical work |
| Validation and iteration | Test assumptions, gather feedback and improve the solution |
| Pitch and communication | Tell a clear story about the problem, solution and impact |
| Demo and competition readiness | Prepare the submission, test the demo and rehearse |

## Team workflow

Recommended lightweight workflow for hackathon teams:

- **Team lead / coordinator:** keeps the team aligned and tracks progress.
- **Product / problem lead:** clarifies users, problem statement and MVP scope.
- **Developers / builders:** implement the core solution.
- **Design / research lead:** supports user journeys, research, usability and feedback.
- **Pitch / documentation lead:** records decisions, maintains project documentation and prepares the demo story.

One member may hold more than one role, especially in small teams. Roles are suggestions, not requirements.

Use GitHub Issues or a shared task board to record tasks. Keep tasks small, assign an owner, and agree on a deadline. Raise blockers early instead of waiting until the end.

## Deliverables and readiness checklist

Use this as a guide; each external competition may have its own requirements.

### Before building
- [ ] Problem statement is clear and specific.
- [ ] Target user or beneficiary is identified.
- [ ] The team can explain why the problem matters.
- [ ] MVP scope is realistic for the available time.
- [ ] Tasks and responsibilities are agreed.

### During building
- [ ] Core user flow is prioritised.
- [ ] Code and project files are stored in a repository where appropriate.
- [ ] Setup instructions are documented.
- [ ] Progress and blockers are communicated.
- [ ] Testing and feedback are recorded.

### Before presenting
- [ ] Prototype can be demonstrated reliably.
- [ ] Pitch explains the problem, solution, users and impact.
- [ ] Team members have practised their parts.
- [ ] Demo has been tested on the presentation device or environment.
- [ ] Backup screenshots or a recorded demo are ready.
- [ ] Limitations and future work are stated honestly.

## Participation guidelines

- Be welcoming to beginners and respectful of different skill levels.
- Focus on learning, collaboration and solving meaningful problems.
- Keep challenge submissions original and acknowledge external code, data, libraries and assets.
- Never include passwords, API keys, private credentials or sensitive personal data in public repositories.
- For cybersecurity challenges, practise only in systems, labs and environments you own or have explicit permission to test.
- Avoid collecting real personal or sensitive data for prototypes unless there is a clear, approved and safe reason.
- Communicate with teammates and organisers if you are blocked or cannot meet a deadline.

## How to contribute

1. Fork or clone the repository.
2. Create a branch for your changes.
3. Add resources or improve documentation in the appropriate folder.
4. Use descriptive file names and include a short description, source link and level where relevant.
5. Open a pull request or submit changes using the process agreed by the organisers.

Before adding a resource, check that it is accessible, relevant and safe to share. Do not upload copyrighted course material unless sharing is permitted; link to the official source instead.
